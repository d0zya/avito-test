E01: пустой фильтр — 0.424584 (630 запросов), непустой — 0.382072 (370). Локальный каталог больше benchmark-каталога (344 825 против 189 212) и состоит из объявлений, встречающихся в положительных парах; прямое сравнение абсолютной оценки с leaderboard ограничено. Следующее изменение выбирается после анализа ошибок E01.

Анализ ошибок E01 на том же holdout: нулевой Recall@50 у 57,0% запросов. Для непустого фильтра — у 59,7%, для пустого — у 55,4%. У запросов с цифрами средний Recall@50 0,2996 (42 запроса; малая подгруппа). Если среди релевантных нет объявления с тем же ID локации, Recall@50 0,3386 против 0,4307 при наличии совпадения. В примерах «спотер» и «обучение пдр» при наличии фильтра в топе оказываются общие объявления категории; текст фильтра сейчас смешан с собственно поисковой фразой в одном TF-IDF запросе. Это наблюдение поддерживает проверку раздельного учета запроса и фильтра, но разница между группами сама по себе не доказывает причинность.

E02: на основном holdout веса фильтра 0.0 / 0.1 / 0.2 дали Recall@50 0.407080 / 0.414113 / 0.428113. При весе 0.2 на запросах с фильтром: 0.434122 против 0.382072 у E01. Парный bootstrap 95% интервал прироста на основном holdout: [+0.009591, +0.030000]; интервал условен, поскольку вес выбран на этой же выборке. Независимое подтверждение: еще 1000 уникальных текстов без пересечения с первым holdout, 630 пустых и 370 непустых фильтров, seed 1042/1043, вес 0.2 зафиксирован заранее. Recall@50 E01 0.378783, E02 0.387783 (дельта +0.009000); на запросах с фильтром 0.363378 → 0.387703. Парный bootstrap интервал подтверждения: [0.000, 0.018]. Эффект сохраняет знак, но его величина нестабильна.

Следующая локальная гипотеза (E03): многоязычный dense encoder сможет найти релевантные объявления без лексического совпадения. Проверить full-catalog Recall@50 и дополнительную полноту по сравнению с E01. Файл для leaderboard создавать только после явного и существенного локального выигрыша; E02 не отправлен, поэтому использована по-прежнему одна из семи попыток.

E03: *локальная проверка на 50 000 объявлениях из train с гарантированным включением всех релевантных ID для 1000 validation-запросов; seed 42 для остальных объявлений. На этом же каталоге E01 Recall@50 = 0.623014, E5 Recall@50 = 0.528835; гибрид с 20 первыми E5 и заполнением до 50 из E01 = 0.648748. Потолок объединения двух top-50 = 0.708026. Чистый dense retrieval существенно хуже E01, а подтвержденный выигрыш гибрида слишком мал для новой отправки. Полный каталог E5 не кодировали. На полном каталоге E01 Recall@50 / @100 / @200 = 0.408855 / 0.488588 / 0.567127: широкий список допускает потенциальный прирост от попарного ранжирования.

E04: обучены все слои E5 на 20 000 уникальных парах query-item из train, исключены 1000 текстов validation-запросов. Один положительный item на текст query; симметричный in-batch contrastive loss, batch 32, 625 шагов, lr 2e-5, max length 96. Поиск остается одноэтапным по dense embeddings, с текстом фильтра в query. На тех же 50 000 объявлениях Recall@50 / @100 / @200 = 0.567939 / 0.676627 / 0.776142. Прирост относительно zero-shot есть, но уступание E01 не оправдывает leaderboard-попытку. Случайные отрицательные объявления внутри batch могут быть слишком простыми; нужен анализ ошибок перед решением о сложных отрицательных примерах.

E05: проверен Rocchio-style pseudo-relevance feedback без обучения на сохраненных E04 эмбеддингах. На тех же 50 000 объявлениях чистый E04 Recall@50 0.567939; среднее top-3 с весом 0.2 дало 0.560915, top-10 с весом 0.5 — 0.552424. С бонусом точного совпадения ID локации 0.10 базовый E04 дает 0.781980; лучший PRF (top-3, вес 0.2) — 0.785732. Эффект слишком мал и наблюдается только с локацией на упрощенном подкаталоге; submission не готовился. Исследовательская гипотеза не подтверждена.

E06: при ограничении времени проверено одноэтапное усиление совпадения ID локации на полном train-каталоге из 344 825 объявлений. Все остальные компоненты E01 сохранены. Recall@50 для множителя `1 + w × match`: w=0.4 → 0.408855, w=1.0 → 0.521964, w=2.0 → 0.602888, w=4.0 → 0.651121. Вес выбран на том же holdout, поэтому оценка прироста оптимистична. Подготовлен `submissions/submission_02_location.csv`. Формат и принадлежность всех item_id benchmark-корпусу проверены. Метод не является чистым encoder: это быстрый fallback после отрицательного E05 и невозможности закодировать 189 212 benchmark items за оставшееся время.

E06 leaderboard: Recall@50 = 0.677459 (вторая отправка; локально 0.651121, дельта +0.026338). Следующая гипотеза — проверить, не был ли множитель локации 4 слишком слабым.

E07: *локальные значения указаны для двух holdout по 1000 непересекающихся текстов запросов, каждый с 63% пустых фильтров. Каталог — все 344 825 уникальных train-объявлений. При весе 4 первый / второй Recall@50 = 0.651121 / 0.633108; при весе 6 — 0.669321 / 0.658108; при весе 8 — 0.675321 / 0.663608; при весе 12 — 0.677821 / 0.669608; при весе 16 — 0.682321 / 0.668608. Вес 12 — разумный компромисс, второй holdout не подтверждает преимущества 16. У 76.2% запросов есть хотя бы один релевантный item в точной локации: в этой группе вес 12 улучшает recall с 0.744511 до 0.791200; при отсутствии локальных релевантных item ухудшает с 0.313368 до 0.296526. Созданы `submissions/submission_03.csv` и `answer.csv`; 2452 уникальных query_id, ровно 50 уникальных item_id в каждой строке, все ID из benchmark-корпуса. Третий leaderboard Recall@50 пользователь сообщил округленно как `0.7`; точное значение не записываем.

В опубликованном репозитории остаются скрипты E01, E02, E06, E07. Пробные Python-скрипты для E03–E05 с encoder остаются локально и исключены из Git по запросу автора решения. Их результаты сохранены выше; эти варианты не участвовали в leaderboard.

План бюджета: 1 — baseline; 2–4 — отдельные локально проверенные гипотезы из ошибок и LB; 5 — более сильный метод при достаточных основаниях; 6 — исследовательский эксперимент, если оправдан; 7 — лучший проверенный вариант или ансамбль. Неиспользованные попытки сохраняются.
